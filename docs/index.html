Observed decisions, not generated ones

A model deciding what to click from raw page text is guessing. Jev asks a narrower question: given the elements the harness actually observed, which single operation advances the goal? The answer is a choice over observed refs, with probabilities attached.

The executor never invents a selector, a coordinate, or a field value. It acts on the ref that Jev selected from the snapshot, then re-observes. The core in src/core has no OpenCode imports, so any harness with element refs can be the hands. Chrome is the documented default, Brave is the fallback, and the loop in this repo has also been exercised through Playwright.

  • Targets are element refs from the latest snapshot.
  • One operation and one target per cycle.
  • Page text is untrusted data, never instructions.
  • No screenshots in the loop; visible text only, truncated near 6,000 characters.
  • Each decision is consumed once. A retry does not double-click.

Fast cycles, small bills

Every cycle asks a bounded multiple-choice question about observed elements. That shape is why navigation stays quick and why cost tracks text instead of pixels.

  • 378–419 msdecision latency in the live trace
  • 0screenshots or image tokens sent to Jev
  • ≤255choices offered per question
  • ≤6,000characters of page text per request

Sub-second decisions

The live trace shows whole decisions returning in 378–419 ms. Jev answers one narrow multiple-choice question over indexed refs, and nothing in the cycle waits on a screenshot to be captured, uploaded, or interpreted.

After an action the loop waits about 50 ms — up to 200 ms when autocomplete suggestions need to appear — then observes and decides again. Navigation moves at the speed of the page, not the speed of a vision model.

Text-only payloads

A cycle sends the URL, title, visible text capped near 6,000 characters, one indexed element table, and the last 10 actions. It never sends screenshots, image tokens, raw HTML, or the full DOM, so prompt size stays flat on heavy pages.

The one generative call — writing a value into a field — goes to a small text model and returns a single short string. Everything else is a choice among at most 255 offered options.

Failures spend nothing

Provider errors and malformed probability distributions throw before the browser is touched, with messages like “no action executed”. A stale page is re-observed instead of acted on, and each decision is consumed once, so a retry cannot double-click or double-type.

The run stops as soon as DONE has visible evidence, and the 60-step budget is a ceiling rather than a target. Fewer wasted actions means fewer cycles to pay for.

The loop, every cycle

The plugin registers a skill that tells the agent exactly how to run this cycle. The same five steps apply on every page.

  1. 01Snapshotchrome MCP, Brave as fallback
  2. 02Decidejev_decide picks one operation and target
  3. 03Write textjev_text only for TYPE_TEXT
  4. 04Actthe MCP executes the chosen ref
  5. 05Wait, repeat200 ms after typing, otherwise 50 ms

Exit conditions: DONE needs visible evidence of every requirement, BLOCKED means no supported operation can progress, and the run stops after 60 steps.

  1. Snapshot and build the action space.

    Read the accessibility tree, then map it to actions[]: {id, kind: click|fill|select|control, node, label, role, value}. Controls for SCROLL_UP, SCROLL_DOWN, and WAIT are always offered.

  2. Ask Jev for one decision.

    Send the goal, the page state, the observed actions, and recent history. One request returns the operation, the matching target, and the probability distribution that produced them.

  3. Resolve text with the small model.

    When the operation is TYPE_TEXT, jev_text writes the exact string from the goal and field context. If no text model key resolves, the call throws and nothing is typed.

  4. Verify, then act.

    Confirm the target ref is still visible before interacting. After typing in a combobox, wait up to 200 ms for suggestions. Otherwise cap the wait at about 50 ms.

  5. Repeat or stop.

    Three no-change, non-wait actions in a row end the run as blocked. A matching result link is not enough for DONE; the requested destination has to be visibly open.

Two tools, one decision each

jev_decide

Operation and target selection for one cycle.

Input

jev_decide input 
{ "goal": "...", "page": { "url": "...", "title": "...",
  "text": "...", "actions": [ ... ] }, "history": [ ... ] }

Returns

decision 
{ "choice": "fill-e23", "operation": "TYPE_TEXT",
  "target": "1", "confidence": 0.97,
  "target_confidence": 1, "latency_ms": 419 }

Key: TYPESAFE_API_KEY, then auth.json provider typesafe. Model: TYPESAFE_MODEL, default jev-latest.

jev_text

Writes the exact string for a TYPE_TEXT target. It never guesses a value and throws when no model resolves.

Input

fieldContext 
{ "goal": "...",
  "field": { "label": "Search Wikipedia", "role": "searchbox", "value": "" },
  "page": { "title": "...", "text": "..." },
  "recent_actions": [ ... ] }

Returns

value 
{ "text": "OpenAI", "model": "opencode/muse-spark-1.3-contributor-free" }

Key resolution order

  1. TEXT_MODEL_API_KEY, with optional TEXT_MODEL_BASE_URL, TEXT_MODEL, and TEXT_MODEL_REASONING; a local server works with a placeholder key.
  2. Free OpenCode Zen models, generated inside OpenCode through one managed helper session — muse-spark-1.3-contributor-free first. Direct API calls to free models are rejected, so this is the only route. Contributor models may use submitted data to improve the model during their free period.
  3. auth.json provider openrouter or deepseek.
  4. auth.json provider opencode-go, which is OpenAI compatible, sends x-opencode-session, and defaults to the cheap deepseek-v4-flash.

Install

Point OpenCode at a local checkout. The plugin ships as TypeScript with zero runtime dependencies and no build step.

opencode.jsonc 
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": ["/path/to/jev-browser"]
}

Then run /jev-browse to seed the loop in the current session, or just ask for browser work: the skill is auto-invoked and the system prompt routes page actions through Jev.

What gets registered

  • jev_decide and jev_text tools in the jev namespace.
  • The jev-browser skill, sourced from skill/SKILL.md.
  • A browser policy in the system prompt: snapshot, decide, then act.
  • The /jev-browse command.

Limits found in live runs

These come from exercising the loop on real pages, not from theory. Know them before you wire the plugin into something new.

255 choices per question

The TypeSafe endpoint rejects oversized action spaces. A Wikipedia main page snapshot produced 622 accessibility nodes and 270 clickable elements; the request failed until the action space was capped.

TypeSafe response, HTTP 400 
{ "detail": "Too many choices. Must have at most 255 choices." }

The live trace above caps each action kind at 100 candidates. Capping by viewport or by relevance works too. The plugin core does not impose a cap, so the harness or the agent loop has to.

Text needs a key

jev_text throws when no text model profile resolves. Values are never hardcoded or guessed by the executor. If your environment has none of the three key sources, TYPE_TEXT decisions cannot complete.

One decision per snapshot

A decision is tied to the refs it was chosen from. If the page changed after the snapshot, take a new snapshot and a new decision. Reusing a stale decision risks acting on a ref that no longer exists.

Visible text only

The loop never sees screenshots. It reasons over visible text, capped near 6,000 characters, plus the element table. Pages that hide meaning behind images or canvas are outside what Jev can decide on.
